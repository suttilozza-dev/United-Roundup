# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

United Roundup — a Manchester United fan news website. Plain static HTML/CSS/JS, no build tools, no framework, no server required. A Python pipeline (`automation/`) runs daily via GitHub Actions to pull news from RSS/YouTube/Google News sources, classify it with the Claude API, and regenerate the homepage's data feed. Deploys via Netlify (deploy preview on every PR, presumably auto-deploy on `main`).

## Commands

**Run the site locally:**
```bash
python3 -m http.server 8000
```
Then visit `http://localhost:8000`. Opening HTML files directly also mostly works, but a server is needed for the nav/footer includes (`fetch()` calls) to resolve.

**Sanity-check a Python file after editing:**
```bash
python3 -m py_compile automation/<file>.py
```
No test suite exists for `automation/`. The closest thing to a test run is:
```bash
cd automation
python3 validate_sources.py      # checks each source URL/feed actually works
python3 fetch_sources.py         # pulls real current headlines into raw_items.json
python3 classify.py --dry-run    # free, keyword-based classification (no API key needed)
python3 update_site_data.py      # writes classified_items.json into assets/latest-data.js
```
Only run `classify.py` without `--dry-run` (the real Claude API path) if `ANTHROPIC_API_KEY` is set — it's the only step in the pipeline that costs money.

**No build/lint step** for the HTML/CSS/JS — there's nothing to compile, and no linter configured.

## Architecture

### Front-end: shared partials via client-side includes

Every top-level page and nested article page (`briefings/*/index.html`, `whos-saying-what/*/index.html`) shares the same nav and footer, but there's no build step to template them. Instead:
- The canonical markup lives in `assets/partials/nav.html` and `assets/partials/footer.html`, with every internal link written **root-relative** (`/about.html`, not `about.html`) so the same partial works unmodified at any page depth.
- Each page has `<div data-include="nav"></div>` / `<div data-include="footer"></div>` placeholders plus `<script src="/assets/includes.js" defer></script>`.
- `assets/includes.js` fetches each partial and swaps it into the placeholder via `outerHTML`, then fires a `partials:ready` event on `document` once all placeholders on the page have resolved.
- Anything that depends on the nav/footer existing (e.g. the mobile menu toggle in `assets/main.js`) must wire up on `partials:ready`, not just `DOMContentLoaded` — the header doesn't exist in the DOM yet at `DOMContentLoaded` time.
- **To add a new shared partial:** drop root-relative markup into `assets/partials/<name>.html`, add a matching `data-include` placeholder, done. No build step.
- `press-room-watch.html` is the one exception — it has its own standalone `prw-header`/`prw-footer` and never used the shared partials.

### Homepage-only header behavior

`index.html`'s `<body>` carries a `class="home"` that nothing else has. It gates CSS in `assets/extra.css` that hides the UR nameplate while the hero banner is on screen and slides it in (as a "back to top" button) once the banner scrolls out of view, via an `IntersectionObserver` in `assets/main.js` that adds `.past-banner` to `<body>`. Don't drop that class when editing the homepage. The X/Facebook/Instagram icons and the "Support United Roundup" (Kit) button live at the end of the nav bar on every page (`.nav-extras` in `nav.html`); because of them the nav folds into the menu button below 1240px (see the "Top nav bar" block in `extra.css`), not style.css's 900px.

### Homepage sections built from the data feed

`assets/home-latest.js` fills the lead card, the news wire, **"United on Screen"** (`#videos .video-grid`, newest videos, max 2 per channel) and **"The Next Generation"** (`#academy .academy-grid`, newest `academy` items) from `LATEST_ITEMS`, using each item's `image` thumbnail. The hand-written cards in `index.html` are only a fallback. The Weekly Roundup and Who's Saying What cards (`.feature-pair`) are hand-edited: update them in `index.html` when a new edition/analysis is published.

### Generated files — never hand-edit

- `assets/latest-data.js` — rewritten daily by the automation pipeline (`update_site_data.py`). Hand edits will be silently overwritten on the next scheduled run.
- `assets/press-room-data.js` and `press-room-watch.html`'s data sections — regenerated by `automation/rebuild_press_room.py` from `automation/press_room_conferences.json` + `automation/press_room_response_counts.json`. Edit those JSON files and re-run the script, don't hand-edit the output.
- `assets/style.css` — a minified Tailwind v4 build artifact, not hand-written source. Custom styles go in `assets/extra.css`.

### The automation pipeline

Runs in this order (see `.github/workflows/source-tracking.yml`, cron `0 0 * * *` UTC plus manual `workflow_dispatch`):
1. `validate_sources.py` — checks every source in `automation/sources.json` actually resolves; reports pass/fail per source, doesn't fail the build.
2. `fetch_sources.py` — pulls current items from RSS feeds, YouTube channels, and Google News fallbacks (for paywalled sites) into `automation/raw_items.json`.
3. `classify.py` — sorts each item into `transfers`/`team`/`academy`/`interviews`/`club`/`videos` via the Claude API (Haiku). Has a `--time-budget` (workflow passes `600`) and checkpoints progress to `automation/classify_checkpoint2.json` if it runs out of time mid-run — but the checkpoint only survives *within* a run; if you see stale-checkpoint issues, check that the item-count guard (discards a checkpoint that doesn't match the current `raw_items.json`) and the post-completion `unlink()` are both intact. Each item's API call is individually try/excepted — a single flaky call degrades to a low-confidence `"club"` classification rather than crashing the whole run.
4. `update_site_data.py` — writes `assets/latest-data.js` (newest 60 items, at most 12 of them videos, plus the newest 8 videos and 6 academy items always kept for the homepage sections; any video the classifier didn't reach is taken straight from `raw_items.json`; if a run finds no videos/academy items it carries over the previous file's). Each item has an `image` URL (https only) extracted by `fetch_sources.py` from `media:thumbnail`/`media:content`/`enclosure`/first `<img>` in RSS, or the YouTube `hqdefault.jpg`. Item IDs are an MD5 digest of the URL (not Python's built-in `hash()`, which is randomized per-process and would give every item a new ID on every run).

`fetch_sources.py` and `validate_sources.py` share their feed-fetching/parsing logic via `automation/feed_utils.py` — don't reintroduce a second copy of that logic in either script.

`automation/rebuild_press_room.py` is a separate, manually-run script (not part of the daily workflow) that rebuilds the Press Room Watch page's data from the two `press_room_*.json` files.

Intermediate/generated pipeline files (`raw_items.json`, `classified_items.json`, `classify_checkpoint2.json`) are gitignored — if you add a new one, gitignore it too.

The workflow's last step commits `assets/latest-data.js` directly to `main` as "United Roundup Bot" if it changed — no PR. This means branch protection rules on `main` that require PRs would need to exempt this bot, or be scoped to just blocking force-pushes/deletions instead.
